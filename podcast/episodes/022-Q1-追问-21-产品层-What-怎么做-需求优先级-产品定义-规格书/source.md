**一句话定义**

产品层 = 把商业层「为什么做」翻译成研发、供应链、测试、销售都能执行的「做什么、做到什么程度、花多少钱」的工程化过程。

**四步流水线**

1. 需求优先级：决定先做什么。
2. 产品定义：决定产品是什么、给谁、解决什么主任务。
3. 产品规格书：决定如何验收，把需求变成可测量规格。
4. 基线评审：决定何时冻结规格、之后如何变更。

**1. 需求优先级：成熟框架**

| 框架 | 公式/用法 | 适合场景 |
| --- | --- | --- |
| RICE | Reach × Impact × Confidence / Effort | 功能价值排序 |
| MoSCoW | Must / Should / Could / Won't | 划清版本边界 |
| Kano | 基本型 / 期望型 / 兴奋型 | 判断哪些功能不做会被骂 |
| WSJF |（业务价值 + 时间紧迫性 + 风险降低）÷ 工作量 | 多项目排优先级 |
| 机会评分 | 痛点强度 × 频率 × 支付意愿 × 可触达性 | 场景和客户排序 |
| 价值-成本矩阵 | 高价值低成本先做 | 快速对齐资源 |

硬件特别提醒：需求工作量要算上研发、模具、认证、供应链和测试，不只算功能开发时间；硬件变更成本远高于软件，所以「冻结时点」也是优先级的一部分。

**2. 产品定义：成熟框架**

| 框架 | 回答什么 |
| --- | --- |
| Product Vision Board | 目标客户是谁、要解决什么、产品是什么、商业目标是什么 |
| JTBD | 客户雇佣产品完成什么任务、成功标准是什么 |
| Value Proposition Canvas | 客户痛点、期望收益、产品如何消除痛点 |
| MVP 定义 | 只做一个主 Job、一个核心场景、最小可靠硬件 |
| Scope 清单 | 明确 In Scope 和 Out of Scope |

输出物：产品定义一页纸，包含目标客户、主 Job、价值主张、版本边界、非目标、商业约束。

**3. 产品规格书：成熟框架**

| 文档/框架 | 用途 |
| --- | --- |
| PRD | 软件功能、交互、业务规则 |
| HRS | 硬件需求：性能、接口、环境、可靠性、成本 |
| System Requirements | 系统级需求和验收标准 |
| ICD | 接口控制文档：物理、电气、协议、软件 API |
| User Stories + Acceptance Criteria | 每个功能可验证 |
| V-Model | 从客户需求拆到系统、子系统、组件，再逐层验证 |
| QFD / House of Quality | 把客户语言翻译成工程规格，并和竞品对比 |

核心原则：规格不能写定性词，要写可测量值。「响应快」不行，要写「数据上报间隔 ≤ 1 秒」；「耐用」不行，要写「MTBF ≥ 100,000 小时」。

**4. 六个规格维度**

| 维度 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 功能 | 产品做什么、不做什么 | 支持 Modbus、MQTT、告警、OTA |
| 性能 | 做到多快、多准、多大容量 | 数据间隔 ≤ 1s、并发 100 台、丢包率 ≤ 0.1% |
| 接口 | 物理和软件怎么对接 | RS485、CAN、以太网、OPC UA、API |
| 环境 | 什么条件下能正常工作 | -30 到 70℃、IP30、9 到 36V、EMC Level 3 |
| 可靠性 | 能用多久、坏了怎么办 | MTBF ≥ 10 万小时、年返修率 ≤ 2%、支持断点续传 |
| 成本 | 允许花多少钱 | BOM ≤ 600 元、含售后成本 ≤ 900 元 |

**一页纸产品规格书模板**

| 模块 | 内容 |
| --- | --- |
| 产品名称/版本 | 名称、SKU、版本 |
| 目标客户与场景 | 客户、主 Job、使用环境 |
| 核心用户故事 | 作为谁，想做什么，以便得到什么 |
| 功能范围 | P0 必做、P1 应做、P2 可做 |
| 性能指标 | 可测量数值 |
| 接口清单 | 物理接口、协议、兼容矩阵 |
| 环境要求 | 温湿度、防护、供电、EMC |
| 可靠性目标 | MTBF、返修率、寿命、保修 |
| 成本目标 | 目标 BOM、loaded cost、NRE 摊销 |
| 非目标 | 明确不做什么 |
| 验收标准 | 每条规格如何测试 |
| 开放问题/风险 | 待验证项和负责人 |

**工业网关示例**

- 需求优先级：P0 为 80+ PLC 协议、4G 上传、实时告警、断点续传；P1 为 OPC UA、Docker、5G RedCap；P2 为视频接入。
- 产品定义：制造版面向多品牌 PLC 工厂，物流版面向冷链车辆；MVP 只做「设备数据自动采集 + 告警 + 报表」。
- 规格书：数据采集间隔 ≤ 1s，工作温度 -30 到 70℃，IP30，MTBF ≥ 10 万小时，目标 BOM ≤ 600 元。

**常见错误**

- 跳过产品定义直接写 PRD。
- 规格写定性描述，无法验收。
- 功能铺太开，P0 变全功能。
- 忽略接口兼容矩阵，现场接不上设备。
- 可靠性和成本没有目标，量产才发现失控。
- 规格冻结后随意变更，没有变更评审。
- 没有验收标准，研发和测试各说各话。

**产品层检查清单**

1. 每个需求是否有优先级和理由？
2. 每个规格是否可测量？
3. 是否做了接口兼容矩阵？
4. 环境、可靠性、成本目标是否都有数字？
5. 成本目标是否倒推出 BOM 上限？
6. 是否有规格冻结时点和变更流程？
7. 是否有验收标准和测试负责人？
